# CR-039 — Discovery: Webhook Row Disambiguation (Composite-Key Lookup)

> **Type**: Discovery / Investigation finding from INV-2026-07-03-04
> **Date**: 2026-07-03
> **Source**: Owner-triggered live campaign send that produced a 3-row LogID collision
> **Status**: 📋 Registered — Discovery complete, planning in progress
> **Severity**: **P1 CRITICAL** (silent data corruption on every multi-recipient campaign)
> **Risk**: HIGH — Dashboard shows false delivery rates on every real campaign

---

## Problem Statement

The webhook status-callback handler in `routers/whatsapp.py::message_status_callback`
looks up a message row by `message_id` alone. This assumes AuthKey's `LogID` is unique
per send. **That assumption is false in production**: AuthKey returns identical LogIDs
for concurrent single-mobile sends. Consequently:

1. Multiple `whatsapp_message_logs` rows share the same `message_id`.
2. `find_one({"message_id": logid})` deterministically returns the first-inserted row.
3. All webhooks for that logid update **the same row over and over**, regardless of which
   recipient they were actually for.
4. Rows 2..N in the same campaign batch **stay `pending` forever**.
5. The dashboard shows a false delivery rate (typically **1/N** on every multi-recipient
   campaign, even when all N messages were successfully delivered on WhatsApp).

The mismatch is detected by the existing sanity check at line 1413 (`mobile_mismatch`)
but the handler only flags it — it still applies the status update to the wrong row.

---

## Live Reproduction (from INV-2026-07-03-04, 2026-07-03)

Jeh's Nest campaign `978d5e03-0b55-4377-9045-3a532ae86755` fired at 08:47:59 UTC with 3
recipients. All 3 `whatsapp_message_logs` rows created with identical `message_id`
`d1cbdc206ce89f7f794575bbd862a27b` and identical `authkey_raw_response`. Both webhook
callbacks (mobiles 919811657657 and 919035133228) matched row 1 (phone 7505242126)
because of the `find_one` behaviour. Backend logs at 08:48:17 and 08:50:33 confirm the
mismatch detection warning fired but the update proceeded.

Final state:
- Row 1 (7505242126) → `delivered` ✅ (but this update was for a DIFFERENT recipient!)
- Row 2 (9035133228) → `pending` ❌ (in reality delivered per webhook 2)
- Row 3 (9811657657) → `pending` ❌ (in reality delivered per webhook 1)

## Options (Sized, One Recommended)

| # | Option | Effort | Impact | Risk |
|---|---|---|---|---|
| **A** ✅ | **Composite lookup `(message_id, customer_phone)` with fallback** — try composite first, fall back to `message_id`-only for legacy rows without a mobile match. On persistent mismatch, verdict `ambiguous_row` and skip. | ~20 LOC | Fixes 100% of duplicate-LogID cases; backward-compatible with all existing rows | **LOW** — composite lookup is strictly narrower than current; fallback preserves current behaviour |
| B | **Add unique index on `message_id`** + retry on collision + regenerate LogID from CRM side | ~60 LOC + migration | Prevents duplicate row insertion, but AuthKey still returns duplicate IDs so we can't authoritatively map webhooks back | HIGH — schema change, migration required, does not solve the webhook-side mapping |
| C | **Introduce a new `send_id` UUID generated by CRM** stored alongside `message_id`; index webhook lookups by both | ~80 LOC + migration | Fully solves; but AuthKey webhook only sends its own `logid`, so CRM must reverse-lookup via composite anyway | HIGH — more invasive than A, no additional benefit |
| D | **Wait for AuthKey to fix duplicate LogID** at their end | 0 LOC | Blocked on 3rd party | UNKNOWN — no ETA, and even if fixed prospectively, historic pending rows remain |

**Recommendation**: Option **A**. Smallest surface area, backward-compatible, fully
resolves both defects (D1 + D2 from INV-2026-07-03-04), does not depend on 3rd-party fix.

## Non-Goals

- ❌ Do NOT change send-side code (`core/whatsapp.py`). We accept that AuthKey may return
  duplicate LogIDs. Fix must be at the receive (webhook) side.
- ❌ Do NOT modify the state machine (`core/whatsapp_status.py`). Its allowed-transitions
  logic is correct and unrelated.
- ❌ Do NOT change the callback audit log (`whatsapp_callback_logs`). All webhooks
  continue to be persisted; only the verdict field will change for previously-ambiguous
  cases.
- ❌ Do NOT introduce a unique index on `message_id`. That would either break existing
  rows or cause send-time insert failures — bigger blast radius than the current bug.
- ❌ Do NOT backfill historic stuck rows in this CR. Recovery is a separate concern —
  goes to CR-039-B (out of scope here) or CR-039-H2 poll-reconciler (deferred).
