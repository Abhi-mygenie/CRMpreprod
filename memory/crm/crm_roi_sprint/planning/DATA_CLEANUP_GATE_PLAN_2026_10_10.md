# Data Cleanup Gate Plan — pre-conditions, per-restaurant discrepancy report, script behaviour, approval & validation
**Date**: 2026-10-10 · **Role**: Planning (docs only, no code, no data writes) · Covers **CR-085-B** (phones / cc), **CR-087** (duplicates + orphan backfill), **CR-101** (hygiene), **PROC-001** (prod validation) · Builds on owner rulings in `DECISIONS_LOG.md` (085-B report-first 2026-10-09; PROC-001; keep-oldest Q4; India-only +91 Q3).

> Hard rule (owner): **no data write on production without a reviewed, approved per-restaurant discrepancy report.** The script refuses to run without an approval file.

---

## 1. Sequencing — fix gaps first, or clean first?

**Recommendation: fix the gaps that *re-create* the mess first → then clean → then add the hard stop (unique index). Do not wait for POS-side gaps.**

| Order | Step | Why in this position |
|---|---|---|
| **0a** | Deploy current batch to prod (CR-085-A/A2, CR-100, CR-109, …) after owner smoke + closure | Prod is still creating null-cc docs (9 in Oct), blank-phone customers and junk via realtime/sync **today**. Cleaning before deploy = re-cleaning next week. |
| **0b** | **CR-111** importer `normalize_phone` + **CR-113** daily data-quality (DQ) job + `phone_invalid` visibility | CR-113 gives a **baseline measurement** of daily leakage *before* cleanup, so after cleanup we can prove the number is zero rather than assume it. |
| **0c** | POS asks P-8 / P-9 / P-15 sent — **not blocking** | P-9 (junk in POS master) only re-imports as *flagged* records, idempotent. P-15 (ID space) blocks **only the Palm-group backfill (~₹46 L)**, which is carved out as its own approval line. |
| **1** | Generate per-restaurant discrepancy reports (read-only) | §2 |
| **2** | Human approval per restaurant (owner + restaurant where flagged) | §3 |
| **3** | Scripted cleanup, per restaurant, dry-run → apply | §4 |
| **4** | PROC-001 production validation | §5 |
| **5** | **CR-112** unique partial index on `(user_id, phone, country_code)` | Can only be created once dup groups = 0; this is what makes "it can't happen again" true at DB level. |
| **6** | 7-day DQ-job watch → closure | Proves no new leakage with the new code + index. |

What **not** to do: run cleanup first "because the numbers are known". Null-cc and junk are still being written daily on prod; and without the DQ job we have no before/after evidence for the owner.

## 2. Per-restaurant discrepancy report (deliverable before any write)

One file per restaurant: `cleanup/reports/<rid>_<restaurant_name>_DISCREPANCY_<date>.xlsx` (+ `.md` summary). Generated by a **read-only** script. Six sheets:

### Sheet 0 — Summary (the page the restaurant owner reads)
| Field | |
|---|---|
| Restaurant, rid, CRM customers, orders, points balance total | baseline snapshot |
| Count per category J / F / T / S / B / D-true / D-twin / CC / O-A / O-B / O-C (see below) | |
| **What will change** in plain words, **what will never change** (no order deleted, no points removed, no customer with history deleted) | |
| Items that need the **restaurant's** decision (J/T/S corrections, Jeh's-type dup groups) vs items the **system** fixes (cc, twins, F re-parse, backfill) | |
| Sign-off block: owner ✔ / restaurant ✔ / date | |

### Sheet 1 — Invalid phones (CR-085-B)
Per customer row: `customer_id · name · stored phone · phone_raw · country_code · pos_customer_id · category · detected_as · orders · total_points · total_visits · last_visit · created_at · source (POS master / CSV / realtime / UI) · proposed_action · needs_restaurant_input (Y/N) · corrected_phone (restaurant fills) · approve (Y/N)`

| Category | Detection | Proposed action |
|---|---|---|
| **J** junk | all-same digit, `1234567890`, `0123456789`, `1000000000`-style | `phone_invalid:true`; nothing else |
| **F** foreign without cc | 11–15 digits, leading digits = known cc (44, 49, 971, 61, 1…) and remainder plausible | `phone` ← national digits, `country_code` ← `+cc`; restaurant confirms country |
| **T** typo Indian | 9 digits; 11 digits starting `91`+9; 12 digits not `91`+10 | flag; restaurant may supply corrected phone |
| **S** short / room-no | < 7 digits | flag; restaurant informed (cashier training) |
| **B** blank | `phone` `""`/null (78 legacy `Customer ` docs) | if 0 orders & 0 points → delete (CR-101); else keep, flag |

### Sheet 2 — Duplicate groups (CR-087)
Per group: `group_id · phone · members (customer_id, name, cc, created_at, pos_customer_id, orders, points, visits, wallet, tags, opt-in) · group_type (true / cc-twin) · keep = oldest (owner Q4) · merge_plan (what moves from loser → keeper) · needs_restaurant_input (Y if ≥2 members have points>0 or visits>0) · approve`

### Sheet 3 — Null / empty country_code (CR-085-B)
Per customer: `customer_id · name · phone · cc_stored · proposed cc=+91 · is_twin_of (if a +91 doc with same phone exists → handled in Sheet 2)`. System fix, listed for transparency.

### Sheet 4 — Orphan orders (CR-087 backfill)
| Sub-type | Rows | Proposed action |
|---|---|---|
| **O-A** customer exists now (match by `pos_customer_id` variants, else `phone_match`) | order_id · pos_order_id · date · amount · pos_customer_id · cust_mobile · matched customer_id · match_by | `$set customer_id` only. **No points, no visits, no spend recalculated** unless owner rules otherwise (default: link only, stats untouched — avoids retro-awarding points) |
| **O-B** no customer yet, has `pos_customer_id`/valid phone | counts only | no action in this run; depends on customer sync / P-15 |
| **O-C** anonymous (blank phone, no pid) | count + ₹ | **no action** (owner ruling 2026-10-10: acceptable) |

### Sheet 5 — Hygiene (CR-101)
Orphan-tenant customers (e.g. `pos_0001_restaurant_69`), dead `password_hash` fields, `customer_otps` collection, legacy blank-phone docs → each with `approve`.

### Sheet 6 — Validation queries (PROC-001 preview)
The exact queries + expected before/after counts for this restaurant (so the restaurant can see what "done" means).

**Also one cross-restaurant file** `cleanup/reports/ALL_RESTAURANTS_SUMMARY_<date>.md` with the 79-row table (already drafted in `PROD_PER_RESTAURANT_BREAKDOWN_2026_10_10.md` §Q2) and the approval status column.

## 3. Approval gate (human)

| Who | Approves | How |
|---|---|---|
| **Owner** | every restaurant file; may approve system-only sheets (3, 4-O-A, F re-parse, twins) in bulk | writes `approved_by/date` in Sheet 0 and returns the file |
| **Restaurant** | only rows marked `needs_restaurant_input=Y`: J/T/S corrections, dup groups with history on both sides, F country confirmation | fills `corrected_phone` / `approve` columns |
| **CRM** | converts the returned file into `cleanup/approved/<rid>_APPROVED.json` (machine-readable: per customer_id / group_id / order_id → action) — **this file is the only input the cleanup script accepts** | |

Rules: unapproved row ⇒ skipped and reported, never defaulted. A restaurant that does not answer ⇒ only system-safe actions (cc fix, twins, F re-parse with unambiguous cc, O-A backfill) run; J/T/S stay flagged (flag is harmless), real dups wait.

Restaurant time required (from prod data): **Jeh's Nest** (94 dup groups with history), **Kunafa Mahal / CAFE 103 / LSD / Craft / Aura / Pav & Pages ×2 / Mill Bakery / mantri** (junk list for cashier), **The Palm House / Cafe Flora** (confirm foreign countries). Everyone else: system-only.

## 4. What the cleanup script will do (`scripts/cleanup/run_cleanup.py` — to be written at the IMPLEMENTATION gate)

**Invocation**: `--restaurant <rid> --approved cleanup/approved/<rid>_APPROVED.json [--apply]` — default is **dry-run**; `--apply` requires `--confirm <rid>` typed again.

**Pre-flight (abort on any failure)**
1. Connected DB name = `mygenie_db` **and** user is the **write** user (not `mygenie_mongo_readonly`); refuses if `DB_NAME` or host differ from the approval file's recorded target.
2. Approval file hash matches the report it was derived from; `approved_by` non-empty.
3. Re-runs the discrepancy detection live and **diffs** against the approved list — any customer/group that changed since the report (new order, new points) is **skipped and listed** ("stale approval").
4. `mongodump` of `customers`, `orders`, `points_transactions`, `wallet_transactions`, `coupon_usage`, `feedback` filtered to this `user_id` → `cleanup/backups/<rid>_<ts>/`. No dump = no run.
5. Writes a `data_cleanup_runs` row `{run_id, rid, started_at, mode, approval_hash, counts_planned}`.

**Actions (in this order, each idempotent, each writes a `data_cleanup_audit` row per document with `before` and `after` snapshots)**

| # | Action | Exactly what is written | Never |
|---|---|---|---|
| A1 | Null cc → `+91` | `$set country_code:"+91"` on approved ids where phone normalises valid Indian | touches phone digits |
| A2 | F re-parse | `$set phone:<national>, country_code:<+cc>, phone_raw:<old>` | runs on ambiguous cc without restaurant confirmation |
| A3 | Flag J/T/S | `$set phone_invalid:true, phone_invalid_reason:<cat>`; if restaurant supplied `corrected_phone` → validate, then `$set phone, phone_raw:<old>` and unset flag | deletes |
| A4 | Merge duplicate group (keep oldest) | for each loser: `orders/points_transactions/wallet_transactions/coupon_usage/feedback/customer_documents.$set customer_id → keeper`; keeper `$set` recomputed `total_points`(from ledger), `total_visits`, `total_spent`, `last_visit`, `wallet_balance`; `tags` union; `whatsapp_opt_in` = keeper's unless null; `pos_customer_id` = first non-null; loser doc **moved** to `customers_merged_archive` (not deleted) with `merged_into` | merges a group with `approve≠Y`; drops any ledger row |
| A5 | O-A backfill | `orders.$set customer_id` (and `order_items.customer_id`) by `pos_customer_id` variants, else `phone_match` | changes customer stats / awards points (owner may rule otherwise → separate approval) |
| A6 | CR-101 hygiene | delete only approved zero-history docs; `$unset password_hash`; drop `customer_otps` | deletes anything with orders/points |

**Post-run**: `data_cleanup_runs` row updated with `counts_done / skipped / errors`, PROC-001 queries executed automatically and stored; prints a human summary; `--apply` run is **refused** if a dry-run with the same approval hash has not completed within 24 h.

**Rollback**: per run, `data_cleanup_audit.before` snapshots + `customers_merged_archive` + the mongodump → `run_cleanup.py --rollback <run_id>` restores documents by `_id`. Rollback itself writes audit rows.

**Scope of the script**: one restaurant per invocation; no cross-tenant query; no index creation (CR-112 is separate); never runs the realtime or sync code paths.

## 5. PROC-001 production validation (after each restaurant, and once globally)

| Check | Query | Expected |
|---|---|---|
| V1 | `customers.count({user_id, country_code:{$in:[null,""]}})` | 0 |
| V2 | dup groups by `(user_id, phone)` with `phone_invalid≠true` | 0 |
| V3 | invalid phones **unflagged** (`normalize_phone` invalid and `phone_invalid≠true`) | 0 |
| V4 | `orders.count({user_id, customer_id:null, pos_customer_id:{$exists}, <customer with that pid exists>})` | 0 |
| V5 | ledger integrity: for every keeper, `total_points == Σ points_transactions` | 0 mismatches |
| V6 | totals conservation: Σ `order_amount`, count of orders, Σ ledger points **before == after** per tenant | equal |
| V7 | no customer with orders/points deleted: `customers_merged_archive` ids ∩ (orders.customer_id) | 0 |
| V8 | all other tenants' counts unchanged (`customers`, `orders`) | equal |
| V9 | app smoke on prod for that tenant: `/api/customers` list, one merged customer detail, POS `customer-lookup` for one corrected phone, Customer App `lookup` | 200 / correct |
| V10 | DQ job (CR-113) next-day row: new dups 0, new unflagged invalid 0, new null-cc 0 | 0 |

Global closure additionally requires: `CR-112` index created without `DuplicateKey` error; 7 consecutive DQ-job days at zero.
