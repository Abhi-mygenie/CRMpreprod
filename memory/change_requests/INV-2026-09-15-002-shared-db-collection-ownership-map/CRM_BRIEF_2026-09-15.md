## 1. Why We Are Raising This

We recently confirmed — through a live MongoDB probe and the INV_017 contract exchange — that **both the Customer App backend and the CRM share the same `mygenie` MongoDB database**.

This is not a problem in itself, but it means both systems are reading and writing to some of the same collections simultaneously. Without a clear, agreed contract of **who owns what**, we risk:

- Silent overwrites of config or data set by one team's admin UI
- Schema drift when either team adds/removes/renames fields
- Accidental reads of stale data after the other team writes
- Blocked migrations (we have a MySQL migration planned; CRM has their own roadmap)
- Security exposure if JWT signing secrets overlap

**The goal of this document is not to claim territory — it is to agree, write down, and respect a clean ownership boundary for every collection.** Both teams benefit from this.

We have done the local analysis on our side. We share our findings fully below and ask four specific questions where only the CRM team can provide the answer.

---

## 2. Context — Architectural Decision Already Made by Owner

The product owner has decided (**Decision D-A, 2026-09-15**):

> **CRM owns the customer surface** (login, profile, orders, points, wallet, addresses).  
> **Customer App owns the app shell** (admin UI, restaurant config, uploads, POS proxy, dietary tags, diagnostics).

This means:
- The Customer App frontend will call CRM `/scan/*` endpoints for all customer-facing data going forward (CR-2026-09-15-001 is the first delivery of this)
- Our backend's `/api/customer/*` routes become retirement candidates — but **only after this ownership map is agreed and signed**
- The Customer App admin UI owns writes to `customer_app_config` (**OD-7**)

We are not making unilateral changes. Nothing moves until both teams have agreed the map.

## 5. Four Questions We Need CRM to Answer

These are blocking our collection ownership map from becoming final. Please answer all four.

---

### Q2 — `customer_app_config` write lock

> **Does your admin UI or any CRM automated workflow actively call `PUT /api/scan/config/{restaurant_id}` today?**

- If **yes**: (a) Which keys does it write? (b) Can this path be made read-only or disabled for the app-config use case? Or would you prefer we agree a partition — CRM writes its own keys, Customer App writes its keys?
- If **no**: Can you formally disable or tombstone this path so it cannot be called accidentally?

This is our highest-priority question. If both UIs write to the same config doc without coordination, one team's admin changes can silently overwrite the other's.

---

### Q4 — `dietary_tags_mapping` write lock

> **Does your admin UI or any CRM workflow actively call `PUT /api/scan/menu/dietary-tags/{restaurant_id}` today, and does this write to the `dietary_tags_mapping` collection in the shared `mygenie` DB?**

- If **yes**: Who should own the write? We can defer to CRM if you are the active writer. We just need to know so we can route our admin accordingly.
- If **no**: Can you confirm you do not write to this collection, so we can safely continue owning it?

---

### Q4b — `feedback` collection

> **Does `POST /api/scan/feedback` write to the same `feedback` collection our backend writes to?**

- This is low priority (append-only, no conflict risk). We just want the map to be complete.
- If they are different collections with the same name, please clarify the collection name your endpoint uses.

---

### Q5 — JWT signing secret overlap *(security — please prioritise)*

> **Is the HS256 signing secret your CRM uses to issue customer tokens (`/scan/auth/skip-otp`, `/scan/auth/login`, etc.) different from the `JWT_SECRET` used by the Customer App backend?**

- **Please answer yes or no only.** Do not share the actual secret value.
- **Why it matters:** If both systems use the same HS256 secret, a CRM-issued customer token could technically be validated by our backend (or vice versa), which is an unintended security boundary crossing.
- **If the answer is "same":** Both teams should rotate to distinct secrets before the next release. We can coordinate timing.

## 6. Proposed Standing Rules for the Shared DB

Once CRM answers the four questions above, we propose codifying the following rules in a shared doc. We are open to CRM's edits.

1. **No new collection created by either team without notifying the other.** A collection name collision on a shared DB has caused data corruption at other companies. One Slack message is enough.
2. **Schema changes to any shared collection** (Group A or B above) require a brief cross-team note before deployment. Adding a new field is fine; renaming or removing is a coordination event.
3. **Index changes** on shared collections require the same lightweight notification.
4. **`customer_app_config`** — single writer once Q2 is resolved. Whichever team does not own writes must treat the endpoint as read-only.
5. **`users`** — Customer App commits to read-only forever. Any admin credential change goes through CRM.
6. **JWT secrets must be distinct** (pending Q5 resolution).
