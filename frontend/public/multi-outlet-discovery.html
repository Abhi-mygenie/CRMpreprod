Multi-Outlet Discovery Layer
How it should work, what we found, and what we need to decide

Customer web app · Prepared from a review of the live code and the preprod APIs · June 2026

Scope: architecture and decisions. The API details shared by backend were treated as a suggestion, not a fixed contract.

1. What we're building In one paragraph

Today every restaurant has its own ordering website (for example 18march.mygenie.online/478). A brand with several outlets wants one front door: the customer lands on the brand page, tells us where they are, sees which outlets can serve them, taps one, and then continues in the existing ordering flow of that outlet — without typing their location again.

Brand page→ "Where are you?"→ Outlets that can serve you→ Existing outlet ordering flow (unchanged)
The most important idea in this document: the new part is only the three orange boxes. The green box is our live, revenue-earning flow. It is not being rebuilt, redesigned, or reworked. The new layer just decides which outlet the customer enters and carries their location across.

2. Ground rules These stay true even if the API changes ten times

We wrote these first, before looking at any API, because the shape of the API will change — but the reasons behind these rules will not.

Rule 1 — The new layer is an add-on. The existing flow does not change.

What it means

We add new pages in front. We do not edit how the menu, cart, address or payment screens behave.

What it solves

This is a live product with real orders. Every line we change in the old flow is a chance to break payments or addresses for customers who never even use the brand page.

What is needed

Discipline in scope. Any change to old screens must be small, optional, and switched on only when the customer arrived from a brand page.

Rule 2 — One answer for "Can this outlet deliver to me, and for how much?" Most important

What it means

Whatever the brand page says ("Outlet A delivers to you, ₹40 fee") must come from the same calculation the outlet's own checkout uses. Not a similar one. The same one.

What it solves

Right now there are two separate systems: the new brand-page system uses a hand-typed list of pincodes; the existing checkout uses the outlet's distance and fee settings. Two systems will disagree. The customer sees "Yes, we deliver" on the brand page, picks the outlet, enters the same address, and gets "Delivery not available". That destroys trust in 30 seconds and we lose the order.

What is needed

Backend reuses the existing distance/fee logic inside the new "check my location" API. Until that happens, the front end will quietly double-check each outlet against the existing fee API before showing the card — so the customer never sees a promise we can't keep.

Rule 3 — Backend tells us which outlet. The website decides how to get there.

What it means

The API should return the outlet's identity (its number, name, and the domain it lives on). It should not return a ready-made link for us to blindly jump to.

What it solves

The backend cannot know which website the customer is standing on. Today the suggested link points at 18march.mygenie.online for every outlet. If the brand page is hosted anywhere else (a brand's own domain, preprod, testing), jumping to that link throws away everything the customer typed. It also means a typo in a database field becomes a broken page for customers, and nobody on the front-end side can catch it in review.

What is needed

Backend returns hostname (can be empty) instead of redirect_url. The website builds the address from that. Meanwhile we can still tolerate the current link by reading the outlet number out of it.

Rule 4 — Carry the customer's location in the web address, not in browser storage.

What it means

When the customer taps an outlet, we open it as /510?orderType=delivery&lat=…&lng=…&loc=Connaught+Place. The outlet page reads that and pre-fills.

What it solves

Browser storage (localStorage) is tied to one domain. If the outlet lives on a different domain, the storage is invisible there and the customer has to type their location again — the exact problem this feature exists to remove. Web-address parameters also survive a page refresh, private browsing, and can be shared as a link.

What is needed

Very little: the app already reads ?orderType= from the address for QR codes. We extend the same reader with a few more fields.

Rule 5 — A brand is found the same way a restaurant is found.

What it means

Restaurants are found by number in the path (/478) or by domain (hyatt.mygenie.online). Brands should work the same: /g/478 or brandx.com.

What it solves

Avoids building a second, parallel way of resolving "who is this page for" that we would then maintain forever. It also handles a real conflict: 18march.mygenie.online is already restaurant 478's website, so the brand page cannot simply sit at / on that domain without a clear rule.

What is needed

Reserve the path /g/ for groups. Backend answers "is this domain a brand or a single restaurant?" in one call.

Rule 6 — Public APIs show only public information. Security

What it means

Anything a visitor can call without logging in must return only what a visitor should see: name, logo, address, timings.

What it solves

On preprod today, the public "get brand" API returns the master restaurant's full internal record — including a live CRM access token, the owner's UPI ID, email, and payment configuration. Anyone with the URL can read this.

What is needed

Backend trims the response to an approved list of fields. This has to be done before anything goes live, regardless of the front end.

Rule 7 — Pages never read the raw API. A translation layer sits in between.

What it means

One small file converts whatever the backend sends into the shape our screens expect.

What it solves

The API will change (that is the plan). With a translation layer, when it changes we edit one file, not every screen.

What is needed

Nothing from backend — this is a front-end practice the app already follows for orders and menus.

3. What we found From the live code and real preprod responses, not from the document

FindingWhy it matters
The suggested redirect link always points to 18march.mygenie.online, even though the brand's configured domain is a placeholder (master-outlet-478.local). If the brand page is hosted anywhere else, the jump crosses domains and the customer's typed location is lost. Also shows the link is not actually derived from the brand's own domain setting.
18march.mygenie.online is already restaurant 478's site. The brand landing page has nowhere to live on that domain without a dedicated path (/g/…) or a rule that says "this domain is a brand, not a restaurant".
Two different "can we deliver?" systems. The new API uses a hand-typed pincode list. The existing checkout uses the outlet's distance, per-km fee, minimum/maximum fee and free-delivery threshold. They will disagree. Customer is told yes, then no. There is also no fee on the brand page, so the customer cannot compare outlets and discovers the fee only at checkout.
Outlet 510 is recorded at Surat coordinates but "delivers" to Delhi 110001 — 1,544 km away — because someone added that pincode to its list. The API also returns "radius 6 km" alongside that 1,544 km distance. Proof that a hand-maintained pincode list can be wrong, and that showing the "radius" figure to customers would look absurd.
Delivery in the existing flow requires login and a saved, complete address (house, floor, contact person). The address screen sends you back if you are not logged in. The brand page captures a rough location ("I'm near Connaught Place"), not a deliverable address. So the handoff must pre-fill the map, not pretend to be a finished address. This changed our earlier plan (see Section 4).
The app already passes order type through the web address (?orderType=delivery) for QR codes. We reuse this exact mechanism for the location. Low risk, proven in production.
The public brand API leaks private data — live CRM token, UPI ID, email, payment settings. Must be fixed by backend before release. Not negotiable.

4. Where we changed our mind Honest corrections to the earlier analysis

Earlier: save the address into browser storage, then redirect

Now: pass the location in the web address; the outlet's address screen uses it to centre the map and pre-select a nearby saved address.

Why we changed

Browser storage breaks across domains, and writing a half-finished address straight into the cart would skip the login and confirmation steps that delivery genuinely needs. The customer must still confirm house/floor/contact — we just make it one tap instead of a search.

Earlier: ask backend to add a "delivery charge" column to the pincode table

Now: ask backend to run the existing distance-and-fee logic inside the new API.

Why we changed

A number typed into a table is not the same as the rule checkout enforces (which depends on distance, order value and time). Only reusing the real rule guarantees the card and the checkout agree.

Earlier: ignore the backend link and build our own

Now: ask backend for the outlet's domain (optional) instead of a link; the website builds the route. Tolerate the current link in the translation layer meanwhile.

Why we changed

Fixes the cause instead of patching around it. Navigation belongs to the website.

Earlier: just add a /g/ path

Now: /g/ path and brand domains, with one resolver that knows whether a domain is a brand or a restaurant.

Why we changed

Real brands will want brandx.com, not something.mygenie.online/g/478.

5. How the customer journey will work Step by step

  1. Customer opens the brand page — either brandx.com or …/g/478. They see the brand's logo, name and a single question: "Where should we deliver?" plus a Delivery / Pickup switch.
  2. Customer gives a location — one of: tap "Use my location", type an area and pick from suggestions, or type a pincode. Whatever they choose, we turn it into map coordinates before asking the backend (so backend always works with a real point, not just a pincode).
  3. We ask backend which outlets can serve that point for the chosen mode. If Pickup was chosen, there is nothing to check — every open outlet is listed by distance.
  4. Before showing the list, we double-check each outlet's fee and availability against the existing checkout logic (until backend does this for us). This is the guarantee that what the card says is what the customer will pay.
  5. Customer sees outlet cards — logo, name, address, distance, open/closed with next opening time, minimum order, delivery fee (or "Free above ₹300"), estimated time, cuisines. Deliverable and open outlets first. If none can deliver, we show the nearest outlet and offer Pickup or "Change location".
  6. Customer taps an outlet — we open that outlet's existing page with the mode and location attached to the web address. Same domain: instant, no reload. Different domain: a normal jump, nothing lost.
  7. Existing outlet flow takes over — exactly as today. The only differences: the address screen's map is already centred where they said, a saved address nearby is pre-selected, and there is an "← All outlets" link to go back. Login, address confirmation, fee calculation, payment — all untouched.
What the customer feels: "I told them once where I am, they showed me which branches can deliver and what it costs, I picked one, and the app already knew where I was." No repeated typing, no surprises at checkout.

6. What we are asking the backend team for In order of importance — with what breaks if we don't

Ask 1 — Remove private data from the public brand API Release blocker

What: return only brand name, logo, cover image, theme colour, master outlet number, which modes are supported, and outlet count.

Why: a live access token and the owner's payment details are readable by anyone today.

If not done: we cannot go live. This is independent of any front-end work.

Ask 2 — Make "check my location" use the same delivery logic as checkout High

What: for each outlet, return whether it can deliver, the fee, the free-delivery threshold and estimated time — computed by the same code that powers the current distance/fee API. Accept the customer's mode (delivery/pickup) and cart value. Coordinates required; pincode optional.

Why: Rule 2. One answer, not two.

If not done: front end keeps double-checking every outlet itself (extra calls, slower list, more moving parts). Works, but it's a workaround we'd carry forever.

Ask 3 — Return the outlet's domain instead of a ready-made link High

What: hostname (may be empty) and slug per outlet. Drop redirect_url and web_url.

Why: Rule 3. The website must own navigation.

If not done: we read the outlet number out of the link and ignore the rest. Fragile, but survivable.

Ask 4 — One lookup that says "this domain is a brand" or "this domain is a restaurant" Medium

What: given brandx.com, answer { type: "group", id: 1 }; given hyatt.mygenie.online, answer { type: "restaurant", id: 300 }.

Why: Rule 5. Lets brands use their own domains.

If not done: brands only work via the /g/478 path. Acceptable for a first release, not for the long term.

Ask 5 — Small clean-ups Low

Start paging at 0 instead of 1 (standard). Send coordinates as numbers, not text. When no outlet can deliver, include the nearest one. Remove the "radius" figure from the public response (confusing next to real distance).

Timing: Only Ask 1 blocks release. Front-end work can start today against the two public APIs that already exist; Asks 2–5 improve it later without changing any screen.

7. Rollout in three steps Each step is complete and production-quality on its own — this is sequencing, not an MVP

StepWhat shipsDepends on
1 Brand landing page, location entry (GPS / search / pincode), Delivery-Pickup switch, outlet list with real fees (via front-end double-check), handoff through the web address, outlet flow reads the location. Nothing new from backend. Uses the two public APIs already on preprod.
2 Address screen pre-fills from the handed-off location; "← All outlets" link; brand domains (brandx.com). Ask 4 (domain lookup).

8. Decisions we need from the team Six questions. Each has a recommendation and what happens if we go the other way.

Context: A brand page needs a web address. It can be a path on our platform (…/g/478), the brand's own domain (brandx.com), or both.

Option A — Path onlySimple, works today, no backend lookup. But brands must share our domain.
Option B — Domain onlyClean for brands, but nothing to test on until backend delivers the lookup.
Option C — Both (recommended)Path for shared hosting and testing; domain for brands that want their own. Same pages either way.

Glossary Terms used above

Brand / Group / Master outletA set of outlets under one name. One outlet is the "master" (the group's owner account).
Outlet / RestaurantA single ordering website as it exists today, identified by a number like 478 or 510.
HandoffThe moment the customer moves from the brand page into an outlet's page, carrying their location and chosen mode.
Web address parametersThe part after ? in a link, e.g. ?orderType=delivery&lat=28.6. Survives refresh and works across domains.
Browser storage (localStorage)A small store in the browser, tied to one domain. Invisible from any other domain.
Translation layerA single file that converts backend responses into the shape our screens use, so screens don't change when the API does.
Double-check / fan-outFront end asking the existing fee API once per outlet before showing the list, so cards never contradict checkout.
