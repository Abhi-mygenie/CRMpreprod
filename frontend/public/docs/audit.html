The five most dangerous facts

1. MongoDB is reachable from the public internet and has already shown a ransomware indicator database.
2. Everything runs in one process — API, scheduler, campaign sends, PDF rendering. No path to horizontal scaling today.
3. Login has a hard dependency on MyGenie preprod SSO — MyGenie down ⇒ every tenant locked out.
4. Multi-tenancy is a convention, not a guarantee — one missed user_id filter leaks tenant data.
5. No monitoring, no alerting, no CI, no verified backups — failures will be discovered by customers.

1 · Security

SEC-01HIGH Publicly exposed MongoDB with active compromise indicator

What: DB on public IP 52.66.232.149:27017, no TLS; READ_ME_TO_RECOVER_YOUR_DATA ransomware DB observed on the server.

Risk / impact at scale: Full customer PII of every tenant exposed to internet scanners; wipe-and-ransom is realistic. Regulatory (DPDP/GDPR) + total trust loss.

Fix: Private subnet/VPC + security-group allowlist; rotate credentials; enable TLS; scoped non-admin app user; forensic snapshot then remove artifact; move to managed Mongo (Atlas) with IP allowlist + encryption at rest.

SEC-02HIGH CORS wildcard with credentials

What: server.py:179 — CORS_ORIGINS=* with allow_credentials=True, all methods/headers.

Risk / impact: Any site can drive the API from a victim browser; CSRF-style attacks against thousands of dashboards.

Fix: Exact origin whitelist per environment; fail startup if * in production.

SEC-03HIGH Unauthenticated public status webhook (HMAC dormant)

What: POST /api/whatsapp/status-callback is public; HMAC code exists (whatsapp.py:1527) but AUTHKEY_WEBHOOK_SECRET is unset.

Risk / impact: Forged delivery statuses corrupt campaign ROI metrics — the platform's core value; storage-flood vector.

Fix: Set the secret (CR-041-F3), activate HMAC, rate-limit per IP, reject unknown logids.

SEC-04HIGH Plaintext password in localStorage

What: LoginPage.jsx:51 stores remembered_password in plaintext. That password is also the tenant's MyGenie POS password (SSO pass-through).

Risk / impact: One XSS or extension = mass credential harvest across two products.

Fix: Remove password persistence (remember email only); "stay signed in" via refresh tokens (SEC-05).

SEC-05HIGH JWT in localStorage, 24h expiry, no refresh/revocation

What: AuthContext.jsx:59; 24h HS256 tokens; no server-side invalidation; password change doesn't kill sessions.

Risk / impact: XSS = 24h uninterruptible account takeover; incident response impossible at scale.

Fix: 15-min access + rotating refresh tokens in httpOnly cookies; per-user token_version checked in get_current_user.

SEC-06HIGH No rate limiting or brute-force protection

What: Verified — no limiter anywhere. Login, 6-digit OTP endpoints, public webhook all unthrottled.

Risk / impact: Credential stuffing (which also hammers MyGenie — they may block the CRM IP, killing login for all tenants); OTP brute-force in ~10⁶ guesses.

Fix: slowapi (Redis-backed): 5/min/IP on login; 3-attempt OTP lockout; CAPTCHA after repeated failures.

SEC-07MED Flat .env secrets; unencrypted tenant credentials in DB

What: AWS keys, Mongo admin creds, JWT secret in plaintext .env; per-tenant AuthKey/Meta tokens unencrypted in users.

Risk / impact: DB breach leaks every tenant's WhatsApp/Meta credentials; rotation effectively never happens.

Fix: Secrets manager at deploy; envelope-encrypt tenant third-party creds (KMS master key); rotation runbooks.

SEC-08MED Static, unhashed, unscoped POS API keys

What: X-API-Key compared against plaintext users.api_key; no rotation/expiry.

Risk / impact: Leaked key = fake order injection → fabricated loyalty points (financial liability) and poisoned analytics.

Fix: Store key hashes + identifying prefix; dual-key rotation windows; per-key usage logging.

SEC-09MED No security headers or dependency scanning

What: No CSP/HSTS/X-Frame-Options; no pip-audit/yarn audit/Dependabot.

Fix: Header middleware or ingress config; automated dependency scanning in CI (MAI-02). Directly reduces SEC-04/05 blast radius.

SEC-10LOW OTP flow hardening review

Fix: 5-min TTL index, max 3 attempts, single-use invalidation, constant-time compare across otp_tokens and customer_otps.

2 · Scalability

SCA-01HIGH Monolith: API + scheduler in one process — cannot scale horizontally

What: APScheduler starts inside the API lifespan. Running 2+ replicas fires the Daily Loyalty job N times (points corruption — financial); only campaigns have an atomic claim.

Risk / impact: Meal-time POS bursts, login storms and campaign fan-out compete in one event loop; a single OOM kills ingestion + scheduler together. Only scaling lever is a bigger box.

Fix: Dedicated worker deployment (ROLE=worker flag — API pods never start APScheduler); distributed locks (Redis SET NX / Mongo lease) for all cron jobs; scale API pods behind ingress.

SCA-02HIGH No message queue — campaign sends run inside the scheduler tick

What: process_due_campaigns() sends inline; coalesce means ticks are skipped while a large send runs — other tenants' campaigns silently slip.

Risk / impact: 1,000 tenants × 1,000 msgs ≈ 10⁶ sends/day through one sequential pipeline; hours of delay; noisy-neighbor degradation.

Fix: Queue (Redis Streams/RabbitMQ/SQS): tick only enqueues; scalable worker pool consumes with per-tenant concurrency, retries and resumable progress in campaign_runs.

SCA-03HIGH Multi-tenancy enforced only by convention

What: Isolation = every query across 21k+ LOC remembering user_id. No enforcing data layer, no isolation tests, one unsharded shared DB.

Risk / impact: One missed filter = cross-tenant data leak — contract/regulatory breach guaranteed to be found by a customer at scale.

Fix: Tenant-scoped data-access helper that force-injects the filter (hotspots first); two-tenant isolation pytest suite over every list endpoint; plan shard key {user_id, _id} for big collections.

SCA-04MED Unbounded / oversized in-memory queries

What: Verified: 5× to_list(None), 6× to_list(10000) — incl. audience resolution (campaigns.py:55) materializing full customer docs.

Risk / impact: Tenants with >10k customers get silently truncated audiences (correctness bug); concurrent previews OOM the process.

Fix: Cursor iteration + projection; count_documents for previews; lint-ban to_list(None).

SCA-05MED No caching layer

What: Dashboard aggregations, loyalty settings, tag catalogs, template maps re-computed per request.

Fix: Redis: tenant-scoped dashboard cache (60–300s TTL) + invalidate-on-write config caches. Same Redis serves SCA-01 locks, SCA-02 queue, SEC-06 limits.

SCA-06MED Hardcoded, racey campaign daily limit

What: DAILY_LIMIT=1000 module constant; enforcement is check-then-act counting at send time (campaigns.py:394).

Risk / impact: Blocks tiered pricing plans; concurrent sends can exceed the cap.

Fix: Per-tenant plan.daily_message_limit; atomic per-day counter ($inc doc or Redis INCR+TTL).

SCA-07MED Untuned Mongo driver / pooling

What: Bare AsyncIOMotorClient(mongo_url) — default pool 100, 30s server selection, no read preference.

Fix: Explicit maxPoolSize, serverSelectionTimeoutMS=5000, retryWrites; replica set with analytics reads on secondaries.

SCA-08LOW CPU-bound PDF rendering in request path

Fix: Pre-render on invoice creation in the worker; serve from S3.

SCA-09LOW Sequential vendor sync loops

Fix: Bounded-concurrency gather (semaphore 5) after confirming vendor rate limits.

3 · Reliability

REL-01HIGH MyGenie SSO is a hard single point of failure for login

What: Every login synchronously calls MyGenie login + profile. MyGenie down ⇒ nobody can enter the CRM.

Risk / impact: Platform availability capped by a third party's preprod uptime; a 2-hour vendor outage = 2-hour platform-wide lockout.

Fix: Timeouts + circuit breaker; degraded-mode login against local password_hash for known users (sso_degraded=true session, POS-fresh features disabled); async profile refresh.

REL-02HIGH Unverified backups — no proven restore path

What: Backup snapshot failures observed 2026-07-02, never re-verified; combined with SEC-01, a wipe is currently unrecoverable.

Risk / impact: Total loss of all tenants' customers, orders, points ledgers (financial liabilities), invoices.

Fix: Automated daily snapshots + oplog PITR; off-account/off-region storage; quarterly restore drills; documented RTO/RPO.

REL-03MED S3 local-disk fallback on ephemeral pod

What: S3_CONFIGURED=False → invoices/logos write to pod disk, which vanishes on restart.

Fix: Production boot fails if S3 unconfigured; disk fallback for local dev only.

REL-04MED Silent failure patterns

What: 40+ broad except Exception blocks; startup index creation (incl. unique/idempotency indexes) silently passes on failure (server.py:41,92,106,120).

Risk / impact: Code believes it has idempotency guarantees it doesn't have; slow silent corruption at scale.

Fix: Unique-index failures abort production boot; others emit alerts (MON-01); narrow exceptions in business paths.

REL-05MED No automatic retry / dead-letter for failed sends

What: Transient AuthKey timeouts permanently fail messages; recovery is manual resend.

Risk / impact: At 10⁶ sends/day, 1% transient failures = 10k/day needing manual intervention.

Fix: With the SCA-02 queue: exponential-backoff retry (timeouts/5xx only), DLQ + daily digest; never auto-retry provider rejections.

REL-06LOW No skipped-tick detection

Fix: Scheduler heartbeat doc per tick; alert when gap > 3 min.

4 · Performance

PER-01MED Live aggregation analytics, no pre-computation

What: Dashboards aggregate raw orders/customers per request (551 LOC of pipelines).

Risk / impact: Growing scans evict the working set and slow POS ingestion (shared DB CPU).

Fix: Nightly rollups into analytics_daily_rollups (user_id, date) + today's delta; heavy reads to a replica.

PER-02MED Missing compound unique webhook index (CR-041-F2)

What: CR-039 lookup uses (message_id, customer_phone) but only single-field sparse index exists; duplicates can re-enter under race.

Fix: Dedupe, then unique compound index with partial filter — ship deferred CR-041-F2.

PER-03MED Unbounded log-collection growth

What: whatsapp_message_logs, callbacks, webhook/cron/pos-event logs grow forever (≈365M msg-log docs/yr at target scale).

Fix: TTL indexes on raw audit logs (30–90d); 12-month cold archival for message logs; documented retention policy.

PER-04LOW N+1 assembly on detail endpoints

Fix: $lookup or parallel gather on hottest endpoints — measure first via MON-01.

5 · Data model

DM-01MED Mixed campaign_id semantics in message logs

What: Legacy rows: campaign_id=run_id; new rows: campaign_id=campaign.id — every query needs a $or forever.

Fix: One-time batched backfill migration, then delete the $or branches.

DM-02MED No DB-level schema validation

What: Pydantic only at the API edge; scripts/migrations write unvalidated dicts.

Fix: Moderate $jsonSchema validators on top-6 collections (required keys + types only).

DM-03LOW Unbounded tag array on users

Fix: Cap at ~200 tags in API; dedicated collection if demand grows.

DM-04LOW Money as floats

What: Discount/GST math on Python floats. Fix: Integer paise (or Decimal128) for new paths; migrate coupon engine only inside a planned, fully-QA'd change.

6 · Maintainability

MAI-01HIGH Hotspot mega-files concentrate change risk

What: pos.py ~2.9k, whatsapp.py ~4k, coupon.py ~2.5k, customers.py ~2.2k LOC — exactly where a missed tenant filter (SCA-03) would hide.

Fix: Planned splits behind pure re-exports, one file per sprint, guarded by existing pytest suites (CR-041-F1 already registered).

MAI-02MED No CI pipeline

What: Verified — no workflows; tests and lint run manually.

Fix: GitHub Actions on PR: pytest, flake8, eslint, yarn build, pip-audit/yarn audit; protected main branch.

MAI-03MED No API versioning on the POS contract

What: External MyGenie POS consumes unversioned /api/pos/*.

Fix: Freeze as /api/pos/v1/* (alias existing paths); breaking changes → v2 with deprecation window; publish OpenAPI subset.

MAI-04LOW Zero frontend tests; oversized pages

Fix: RTL smoke tests for login, campaign create, template submit; opportunistic component splits.

7 · Deployment

DEP-01HIGH No production pipeline, branch model, or staging

What: Production deployment is UNKNOWN; git = throwaway session branches, no main/tags; the preview pod is the integration environment and points at live preprod data.

Risk / impact: No reproducible ship or rollback; bad deploys hit live tenant data immediately.

Fix: main + feature branches + tagged releases behind CI; staging env with anonymized DB copy; production runbook (build → promote → smoke → rollback).

DEP-02MED Dev-grade serving

What: CRA dev server + Uvicorn --reload (fine for preview, not prod).

Fix: yarn build → CDN/static hosting; uvicorn --workers N without reload; CI-built container images.

DEP-03MED No boot-time config validation

What: Some vars fail fast, others silently default/dormant (webhook secret, scheduler flag, S3).

Fix: pydantic-settings config module; production boot fails loudly on missing/insecure values (CORS *, unset secrets, S3 off).

DEP-04LOW Single region, no DR posture

Fix: After REL-02: multi-AZ replica set + restore-to-new-region runbook.

8 · Monitoring & observability

MON-01HIGH No error tracking, metrics, or alerting of any kind

What: Plain stdout logging only; no Sentry/Prometheus/uptime checks/alert channel.

Risk / impact: Every failure in this document is invisible until a customer complains; MTTD measured in days.

Fix (ROI order): 1) Sentry FE+BE. 2) Structured JSON logs with tenant_id/request_id. 3) /metrics (latency, error rate, tick duration, queue depth, send ratio). 4) Alerts on health-down, error spikes, heartbeat gaps, webhook surges.

MON-02MED No audit trail for staff actions

What: Coupon/loyalty/campaign config changes are unattributed.

Fix: Append-only audit_logs (actor, action, entity, before/after) via decorator on mutating endpoints of critical routers.

MON-03MED Health check is a constant

What: /api/health returns healthy unconditionally — no DB ping, no readiness semantics.

Fix: /health/live vs /health/ready (Mongo ping + scheduler heartbeat age) wired to K8s probes.

MON-04LOW Job logs unconsumed

Fix: Derive metrics/alerts from cron_job_logs; small owner-facing system-status page.
